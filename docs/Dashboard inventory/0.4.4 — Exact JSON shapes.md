## 0.4.4 — Exact JSON shapes

The four payloads, key by key, with the producer cited for every line. Every
fact below is either a `path:line` reference or a value taken from the real
producer run over both fixtures (see **Source and how it was produced**). The
shapes are written as **the producer's own dict literals**, not as an
inference from the JS that reads them: the JS is a reader, and a reader's
`|| ''` is not a contract.

**Source and how it was produced.** Both fixtures were run through the real
producer, with no intermediate layer:

```
core.db.get_dashboard_data(path)          -> 6-key dict
tools/story_dashboard._compute_screenplay_stats(data['screenplay_text'],
                                               scene_ids=data['screenplay_scene_ids'])
                                          -> 7-key dict
_build_title_page(data['title_page'])     -> titlePage, injected by _render_dashboard
_render_dashboard(data, ...)              -> the 4 injections, in order
```

The two fixture payloads were dumped and kept in the scratch directory while
writing this section; the numbers below are from them, and the assertions are
re-runnable (see the reproduction note at the end).

### 0.4.4.1 — `__STORY_DATA__` = `data['story_data']`

`tools/story_dashboard.py:359`, producer `core/db.py:1351` (the `story_data`
literal is `core/db.py:1350-1363`). Twelve top-level keys, in this order:

| key | type | producer | notes |
|---|---|---|---|
| `project` | object | `:1351` | the project entity, flattened; see below |
| `characters` | array | `:1352` | `[]` when none |
| `scenes` | array | `:1353` | `[]` when none |
| `locations` | array | `:1354` | `[]` when none |
| `plots` | array | `:1355` | each entry gets a computed `value_focus` |
| `worlds` | array | `:1356` | `[]` when none |
| `acts` | array | `:1357` | each entry gets a computed `value_focus` |
| `sequences` | array | `:1358` | each entry gets a computed `value_focus` |
| `relationships` | array | `:1359` | `[]` when none |
| `story_memory` | object | `:1360` | `get_memory_block` (`core/db.py:274`) |
| `values` | array | `:1361` | `[]` when none |
| `scene_beats` | array | `:1362` | whole records, not pointers |

**`project`** (`core/db.py:1307-1325`, flattened at `:1056-1064`). The
`_entity_dict` base (`id`, `name`, `one_sentence`, `status`, `order`,
`parent_id`) plus every `extra` key not already present, plus the computed
counts and the computed focus:

```
id, type, name, one_sentence, order, status, parent_id, location_id,
extra, logline, memory, <every extra key not already listed>,
scene_count, character_count, location_count, world_count, plot_count,
sequence_count, act_count, value_focus
```

- `logline` is filled from `one_sentence` when empty (`:1309-1311`).
- `act_count` is `max(_coerce_number(project.act_count, 3), len(acts))`
  (`:1325`) — **not** `len(acts)`. A project that declares 3 acts and has 2
  stores `act_count: 3`.
- `location_id` is in the base dict (`:1005`) and is `null` on every entity in
  both fixtures; it is a column (`core/db.py:27`) that no fixture fills.
- `extra` is carried **whole**, so it repeats keys already flattened at top
  level (`memory`, `id`, and in the live project `screenplay_title`, `credit`,
  `author`, `contact`, `draft_date`, `draft`). A port must read the top level,
  not `extra`.

**Entity arrays — the per-type key set.** The base is always
`{id, name, one_sentence, status, order, parent_id}` (`_entity_dict`,
`:1054-1065`), with `extra` keys merged at top level, then type-specific keys:

| type | additional keys (producer) |
|---|---|
| `character` | `story_role`, `scenes` (`:1090-1100`), `relationships` (`:1240`) |
| `scene` | `title` (`:1108`), `sequence_id` (`:1109`), `act_id` (`:1110`), `dramatic_role`, `heading`, `time_of_day`, `type` (from `extra`), `value_turns` (`:1118`), `characters` (`:1112`), `locations` (`:1113-1115`), `plots` (`:1116`), `milestone` (`:1117`), `scene_objective` (`:1125`) |
| `location` | `variant_of` (`:1136`), `scenes` (`:1141-1149`), `mood`, `dramatic_function` |
| `plot` | `setups`, `inciting_incident`, `complications`, `crisis`, `climax`, `resolutions` (`:1171`), `characters` (`:1174`), `plot_scope`, `plot_type`, `value_arc`, `value_focus` |
| `world` | `variant_of` (`:1183`), `rules`, `period`, `values`, `power` |
| `act` | `title` (`:1191`), `act_objective`, `sequences_list`, `scenes_list`, `sequence_count`, `scene_count`, `plots`, `value_focus` |
| `sequence` | `title` (`:1199`), `act_id` (`:1200`), `primary_plot`, `purpose`, `scenes_list`, `scene_count`, `plots`, `value_focus` |
| `relationship` | `characters` (`:1208`), `perspectives` (`:1209`), `scenes` (`:1210`), `history` (`:1211`) |
| `value` | `p`, `c`, `cd`, `nn`, `note` (`:1216-1222`) — **only these**, plus `id`/`name` |
| `scene_beats` | the record's own `extra`, whole (`:984`) |

**`type` is a per-entity field, not a constant.** `scene.type == "scene"`,
`act.type == "act"`, `sequence.type == "sequence"` (from `extra.type`); the
fixture's `scene_beats` records carry `type: "scene_beats"` while the live
project's do not — the field is whatever was stored, not added by the
producer.

**Nested shapes** (all observed in both fixtures):

```
character.scenes[]            {id, title, heading}
character.relationships[]      {with, label, type, strength}
scene.characters[]             string[]            (character ids)
scene.locations[]              string[]            (location ids; the column value appended if absent)
scene.plots[]                  {id, role}          — a scene can repeat a plot id with a different role
scene.milestone[]              string[]            — main-plot roles only (core/db.py:223)
scene.value_turns[]            {plot, value, from, to, effects:[{character, levels:[{conflict_level, effect}]}]}
location.scenes[]              {id, title, heading}
plot.<beat field>[]            {scene_id, description}
acts[].plots[] / sequences[].plots[]   {id, has_setup..has_resolution, plot_scope, plot_type, value_arc}
relationship.perspectives      {characterId: {feeling, label, type, strength, secret?}}
scene_beats.true_character[]   {character, dilemma, choice_reveals}
scene_beats.changes[]          {entity, change}
scene_beats.beats[]            {action:{by,surface,subtext}, reaction:{by,surface,subtext}, gap}
project.value_focus / plots[].value_focus / acts[].value_focus / sequences[].value_focus
                               {major: [{value, scenes, plots: string[]}], minor: [...]}
```

**`story_memory`** (`core/db.py:274-283`): `{status: "ready", usage: "N/3000",
counts: {decisions, directions, open_questions, continuity_warnings},
categories: {same four keys: string[]}}`. `usage` is the serialized-frontmatter
length (`:257-262`), and the four categories are the closed set
`MEMORY_CATEGORIES` (`core/constants.py`). The JS normaliser's default
(`core.js:85`) is a **shallower** shape (`counts: {}`, `categories: {}`).

**Normaliser contract.** `core.js:88-96` coerces seven collections to `[]`
(`characters`, `locations`, `plots`, `scenes`, `worlds`, `values`,
`relationships`, `story_memory`), `:63` coerces `s.title`, `:69` normalises
`locations` from a string or array, `:76` moves `locations` that are heading
strings into `loc._scene_headings` (`utils.js:3-12`, `:9-14`). The producer
already emits arrays, so the coercion is a guard, not a transform .

### 0.4.4.2 — `__SECTIONS__` = `data['sections']`

`tools/story_dashboard.py:363`, producer `core/db.py:1366-1377`:

```
{ entityType: { entityId: { heading: body } } }
```

- `entityType` is the entity's **type column**, so the keys are the same set as
  the `story_data` arrays plus `project`: observed in both fixtures —
  `project`, `act`, `sequence`, `scene`, `character`, `location`, `world`,
  `plot`, `relationship`, `value`, `scene_beats`.
- `entityId` is the entity's id (a slug), and it is the same id the
  `story_data` arrays carry — the two payloads join on it.
- `heading` is the section heading string, and `body` is the raw text.
- Insertion order is `ORDER BY s.entity_id, s.rowid` (`:1369`), so a type's
  entity order follows the first entity's rowid, not the entity order. **Key
  order is not stable across imports** — observed: the fixture emits
  `act, scene, scene_beats, character, ...` and the live project emits
  `act, project, scene, ...`.
- A heading may be absent for an entity (an entity with no sections is absent
  from its type's map entirely). Both readers already guard this
  (`panel-manager.js:22`, `entity-panels.js:426`).
- **`Content` is the one heading the screenplay is built from**
  (`core/db.py:1385`), and it is the heading `renderSectionsHtml` and the
  scene panel read.

### 0.4.4.3 — `__SCREENPLAY_STATS__`

`tools/story_dashboard.py:373`. Two producers in sequence, and the order
matters:

1. `_compute_screenplay_stats(screenplay_text, scene_ids=...)`
   (`tools/story_dashboard.py:44`) returns the **7 keys below**.
2. `_render_dashboard` **replaces** `titlePage` in place
   (`tools/story_dashboard.py:372`) with `_build_title_page(project_frontmatter)`
   (`:245`). The lexer's own `title_page` is discarded — it is always the empty
   default on both fixtures, because the screenplay text is built from scene
   `## Content` bodies and never carries a Fountain title block.

So the injected object has **8 keys**, and `titlePage` is **not** the lexer's:

| key | producer | shape |
|---|---|---|
| `lengthStats` | `:62-68` | `{pagesWhole, scenes, words, characters, lines}` — all ints |
| `durationStats` | `:88-94` | `{total, action, dialogue, lengthchart_action[20], lengthchart_dialogue[20]}` |
| `characterStats` | `:121-125` | `{characterCount, monologues, characters[]}` |
| `locationStats` | `:149-161` | `{locationsCount, locations[]}` |
| `sceneStats` | `:184-188` | `{scenes[], typeCounts, timeCounts}` |
| `titlePage` | `:245-261` | `{tl, tc, tr, cc, bl, br, hidden}` — **replaced** |
| `scriptHtml` | `:202` | a string of pre-rendered Fountain HTML |
| `sceneIds` | `:212` | the `screenplay_scene_ids` list, positional |

**Nested shapes:**

```
lengthStats            {pagesWhole:int, scenes:int, words:int, characters:int, lines:int}
durationStats          {total:float, action:float, dialogue:float,
                        lengthchart_action:[float;20], lengthchart_dialogue:[float;20]}
characterStats.characters[]   {name, color, speakingParts:int, secondsSpoken:float,
                               wordsSpoken:int, monologues:int}
locationStats.locations[]     {name, color, number_of_scenes:int,
                               interior_exterior:["int"|"ext"], times_of_day:[string]}
sceneStats.scenes[]           {text, number, locType:"int"|"ext"|"mixed"|"other", locTime:string}
sceneStats.typeCounts         {int:int, ext:int, mixed:int}
sceneStats.timeCounts         {lower(time_of_day): int}   — dynamic keys
titlePage.cc[]                {text, type, unfilled?}     — and tl/tc/tr/bl/br/hidden
sceneIds                      string[]
```

**`titlePage`** is `_build_title_page`'s output (`:245-261`), not a parsed
structure. Six fixed slots; `tl`, `tc`, `tr` are **always empty** (the function
returns `[]` for all three), and the other three are built by `_slot`
(`:224-242`):

```
tl: [], tc: [], tr: [],
cc: [title, credit, author]                  # screenplay_title, credit, author
bl: [draft_date, draft]
br: [contact]
hidden: []
```

Each slot is a token: `{text, type}` when filled, or
`{text: "<Label>: N.A.", type: "<type>_unfilled", unfilled: true}` when empty
(`UNFILLED = "N.A."`, `core/constants.py:389`). `type` is `title`, `credit`,
`author`, `draft_date`, `draft`, `contact`. **The first `cc` entry is the
title only because it is written first** — the consumer finds it by `type`
prefix, not by position (`script-view.js:31-32`).

**Empty-input behaviour** (measured, not assumed): `_compute_screenplay_stats("")`
returns a full dict — `pagesWhole: 1`, `lengthchart_*` two arrays of 20 zeros,
`typeCounts: {int: 0, ext: 0, mixed: 0}`, `timeCounts: {}`, and the lexer's
empty `titlePage`. So the stats object is never `null` for empty text; the
`if scene_text:` gate at `:368` is what keeps a project with **no** scene
content from injecting `__SCREENPLAY_STATS__` at all, and then
`script-view.js:11` renders the empty state.

### 0.4.4.4 — `__STRUCTURAL_STATS__` = `data['structural_stats']`

`tools/story_dashboard.py:379`, producer `core/db.py:1471-1479`:

```
{sceneCount:int, sequenceCount:int, actCount:int, sceneStatus:{}, sceneRoles:{},
 plotCoverage:[], acts:[]}
```

| key | producer | shape |
|---|---|---|
| `sceneCount` | `:1472` | `sum(sceneStatus.values())` — the count of **non-deleted scenes** |
| `sequenceCount` | `:1473` | `COUNT(*) WHERE type='sequence'` |
| `actCount` | `:1474` | `COUNT(*) WHERE type='act'` |
| `sceneStatus` | `:1392-1395` | `{status: count}` — **dynamic keys**, one per status value present |
| `sceneRoles` | `:1409-1417` | `{role: count}` — the six `plot_*` kinds minus the prefix, plus `transition` and `non-event` |
| `plotCoverage` | `:1477` | `[{id, name, plot_scope, plot_type, value_arc, sceneCount, coveragePct}]` |
| `acts` | `:1478` | `[{id, title, sceneCount, sequenceCount}]` |

- `sceneRoles` keys are `PLOT_ROLES` (`core/constants.py:24`) with the
  `plot_` prefix stripped (`:1409`), plus `transition` and `non-event` counted
  from `extra.dramatic_role` (`:1413-1417`). A role with no scenes is **absent**,
  not zero — `statistics.js:190-200` therefore renders only the roles present.
- `sceneStatus` and `sceneRoles` are the two dynamic-key maps.
- `plotCoverage[].coveragePct` is `round(sceneCount / len(scenes) * 100)`
  (`:1465`), `0` when there are no scenes.
- `acts[].title` is the act's **name** (`:1446`), not the `title` alias.

### 0.4.4.4a — Defect: the plot's beat fields are keyed by *both* names, and the JS's plural rule is wrong for three of the six

`showPlotPanel` builds its role sections with a naive pluralisation
(`src/dashboard/js/panels/entity-panels.js:280`):

```js
const html = renderBeats(plot[r + 's'] || plot[r] || []);
```

`PLOT_ROLES` (`core/constants.py:24`, mirrored in `colors.js:39`) is
`setup, inciting_incident, complication, crisis, climax, resolution`. The
producer's field names (`PLOT_BEAT_FIELDS`, `core/entity.py:354`, built from
`_RELATION_FIELDS["plot"]` at `:337-343`) are:

| role (`r`) | `r + 's'` the JS tries first | the producer's field | which branch wins |
|---|---|---|---|
| `setup` | `setups` | `setups` | the plural — correct |
| `inciting_incident` | `inciting_incidents` | `inciting_incident` | the **singular** fallback |
| `complication` | `complications` | `complications` | the plural — correct |
| `crisis` | `crisiss` | `crisis` | the **singular** fallback |
| `climax` | `climaxs` | `climax` | the **singular** fallback |
| `resolution` | `resolutions` | `resolutions` | the plural — correct |

**So three of the six role sections are rendered by the fallback, not the
plural.** It works today only because the fallback `plot[r]` happens to be the
producer's actual name for those three. It is a latent break: the plural branch
is evaluated first, so any producer that renamed `crisis` → `crises` (the
natural plural) would make `plot['crises']` win and `plot['crisis']` become
dead — with no error, because both branches are `||`-guarded.

**The `scene.plots[]` role is the singular.** Every entry in `scene.plots[]`
carries `{id, role}` where `role` is the **singular** role name
(`core/db.py:1043`, `role = kind.replace("plot_", "")`), so `scenes.js:45` and
the scene panel at `entity-panels.js:444` read `p.role` directly.

### 0.4.4.5 — Injection order, and the two truthiness gates

`_render_dashboard` builds the injections in this order
(`tools/story_dashboard.py:359-379`):

```
window.__STORY_DATA__        always
window.__SECTIONS__          only if data['sections'] is truthy   (:362)
window.__SCREENPLAY_STATS__  only if data['screenplay_text'] is truthy (:368)
                             and only if _compute_screenplay_stats returns non-None (:371)
                             and only if no exception (:374)
window.__STRUCTURAL_STATS__  only if data['structural_stats'] is truthy (:378)
```

All four are concatenated into one string and spliced at the boot marker
(`:392`). So a port's endpoint must reproduce **the gates, not just the
shapes**: a project with no scene content gets no `__SCREENPLAY_STATS__`, and
the JS must handle its absence (it does — `script-view.js:11`,
`statistics.js:15-19`).

**The whole injection is a single string.** There is no per-payload
serialisation step the port can reuse independently; the four `json.dumps`
calls are inline (`:359`, `:363`, `:373`, `:379`).
