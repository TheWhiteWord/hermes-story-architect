# Phase 2: Hermes Integration

> Prerequisites: `00-overview.md`, Phase 1 and 1b complete. Same working rules as before: the code wins over the plan; **Must** = requirement, **Guidance** = adapt freely; log deviations in `docs/plan/NOTES.md`.

## Outcome

1. The running app exposes the story tools to any MCP client at `http://127.0.0.1:8731/mcp`, protected by a bearer token.
2. One command, `story-architect hermes setup`, prepares Hermes: creates a dedicated agent profile, gives it a persona (`SOUL.md`) and a skill, and registers the app as an MCP server for that profile.
3. The owner starts the app, opens Hermes with that profile (Desktop or CLI), chats, and the agent reads and edits the story through the app's tools.
4. The browser UI shows when the agent has changed something, so the two windows stay in sync.

Chat still happens in Hermes' own interface. The in-app chat is Phase 3.

## Out of scope

In-app chat, manual editing, a Fountain writer, systemd/autostart of the app, other harness adapters, changes to the tool behavior itself (only how they are exposed).

## Design decisions for this phase

- **One process.** The MCP endpoint is mounted on the same server and the same `create_app` factory as the UI/API. No second process, no stdio bridge.
- **Tools are exposed generically.** The 10 existing tool modules are registered into MCP by a loop over their existing definitions (name, description, input schema, handler). No per-tool glue code. The handler is called as `handler(args, root_path=<projects root>)` and its JSON-string result is returned as-is.
- **MCP tool names drop the `story_` prefix** (Hermes adds `mcp_<server>_`, so server `story` plus `story_load` would read `mcp_story_story_load`). Internal names do not change. The mapping lives in one place. If Task 1 shows Hermes handles this differently than the docs say, adjust and note it.
- **Auth:** the `/mcp` endpoint requires `Authorization: Bearer <token>`. The token is generated by `hermes setup` (or on first need), stored with owner-only permissions in the app's config directory, and written to the Hermes profile's `.env` as `STORY_ARCHITECT_TOKEN`; the Hermes MCP config references it as `${STORY_ARCHITECT_TOKEN}`. The existing `Host` validation applies to `/mcp` too. The browser UI/API stay token-free (read-only).
- **The app must be running** for the agent to have its tools. This is accepted for now; document it. (Autostart is a later, separate decision.)
- **Hermes knowledge lives only in the adapter** (`story_architect/adapters/hermes/`). The rest of the package stays harness-agnostic. Adapting the "no Hermes" check: the adapter package and docs may mention Hermes; nothing else may.

### Task 2: MCP endpoint in the app

**Must**
- Mount an MCP Streamable HTTP endpoint at `/mcp` inside the existing app factory (still one process, still `create_app(config)` for tests).
- Register all remaining tool modules generically, with the `story_`-less names, descriptions and input schemas taken from the existing definitions. Tool handlers are blocking, so run them off the event loop (threadpool) rather than directly in async code.
- Bearer-token check on `/mcp`: 401 without/with a wrong token; constant-time comparison.
- Token management in a small module: generate (cryptographically random), persist with `0600` permissions in the app config dir, load. A CLI-less way to read it is not required; `hermes setup` handles distribution.
- Errors: a tool returning `{"success": false, ...}` stays a normal result (the agent reads it); an unexpected exception becomes an MCP error with a useful message and a logged traceback.

**Guidance**
- Keep this in its own module (for example `app/mcp_server.py`), and let the factory include it. The registry that turns tool modules into MCP tools should be small and independently testable.
- Don't change any tool's behavior. If something about a tool blocks generic registration, normalize in the registry and note it.

### Task 4: Hermes adapter, setup command

**Intent:** `story-architect hermes setup` does everything needed on the Hermes side, safely and repeatably.

**Must**
- Lives in `story_architect/adapters/hermes/`. The CLI gets a `hermes` subcommand group (`setup`, `status`); keep the launcher's existing behavior unchanged.
- `setup` steps, each idempotent (re-running is safe and reports what it changed vs. skipped):
  1. Locate the `hermes` executable and read its version; clear error if missing. Respect `HERMES_HOME` if set.
  2. Create the profile (default name `story-architect`, `--profile NAME` to change) if it doesn't exist, cloning config so it has a working model (see H4).
  3. Write the persona to the profile's `SOUL.md`. **Never overwrite an existing `SOUL.md` that was not written by this adapter** without `--force`, and back it up when forcing. Mark adapter-written files (a comment/marker) so updates are recognizable.
  4. Install the skill into the profile's `skills/` directory (same overwrite rules).
  5. Ensure the token exists (Task 2), write `STORY_ARCHITECT_TOKEN` to the profile's `.env` (do not echo it), and register the MCP server (name `story`, URL of the configured port + `/mcp`, bearer header via `${STORY_ARCHITECT_TOKEN}`) using the official `hermes mcp`/`config` commands where they work non-interactively; edit the profile's YAML directly only if the CLI can't, and do it safely (parse, update the `mcp_servers.story` entry only, write back).
- `--dry-run` prints the planned actions without changing anything.
- Never touches other profiles. Never modifies the **default** profile's `SOUL.md`. If the owner passes `--profile default`, only the MCP registration and the skill are applied (no persona), with a clear message about why.
- All Hermes interaction goes through one small wrapper (subprocess calls + path helpers) so it can be faked in tests.

**Checklist**
- [x] `hermes setup` with idempotency, `--dry-run`, `--force`, `--profile`
- [x] Overwrite protections for `SOUL.md` and skill files
- [x] Token distributed without being printed
- [x] Tests using a fake `hermes` executable on `PATH` and a temporary `HERMES_HOME`: first run, second run (no changes), foreign `SOUL.md` preserved, `--force` backs up, dry-run changes nothing, missing hermes error

### Task 5: Persona and skill content

**Intent:** the agent behind the app is deliberately designed, not accidental.

**Must**
- Ship the content as plain files in the adapter (`assets/SOUL.md`, `assets/skills/story-architect/SKILL.md`, plus any `references/` files the skill needs), versioned with the code.
- `SKILL.md` has valid Hermes frontmatter (`name`, `description`, optional `metadata.hermes`).
- Content requirements:
  - **SOUL.md:** who the agent is (a story/screenplay development collaborator working inside Story Architect), tone, how it collaborates (proposes before committing, asks when intent is unclear, respects the owner's creative authority), and the boundary that it works on the story through the tools and does not invent data outside them. Keep it short and durable; workflow detail belongs in the skill.
  - **SKILL.md:** how to use the tools well: the typical workflow (orient on the project, retrieve before answering, stage changes with the draft protocol and commit only after the owner's approval, when to search vs load), how to refer to the app (`dashboard_link`), and the tool descriptions. Derive it from the real tool descriptions and conventions in the repo rather than inventing behaviors. Reference tools by the names the agent actually sees (from Task 1).
- Tests: the frontmatter parses; every tool name mentioned in the skill exists in the registry.

**Owner step:** review `SOUL.md` and `SKILL.md` and adjust the tone. These are the most personal part of the setup.

**Checklist**

### Task 7: Agent changes visible in the browser

**Intent:** with Hermes in one window and the app in the browser, the owner sees when the agent changed the project.

**Must**
- The server notifies the UI when a project's database has changed since the page last loaded, via a lightweight mechanism (Server-Sent Events from an endpoint such as `GET /api/projects/{slug}/events`, or short polling if you judge it simpler and equally reliable). Detect changes with a cheap signal (`PRAGMA data_version` on a read connection, or file modification times for the DB and WAL), not by diffing data.
- The UI reacts without losing the owner's place: **minimum acceptable** is a small, unobtrusive "Project updated, refresh" indicator that re-fetches the dashboard payload and re-renders while preserving the active tab/view. Automatic refresh is welcome only if it preserves state and does not disrupt typing or reading.
- Reconnect behavior is sane (the server restarting does not leave the UI broken).

**Guidance:** keep it small. If the existing vanilla UI makes a clean "re-init with new data" hard, implement the minimum and note the limitation.

**Checklist**

- [x] UI indicator and state-preserving refresh

## Definition of done (acceptance)

1. Fresh state: `pip install .`, `story-architect seed-demo`, `story-architect` running, `story-architect hermes setup` succeeds, and running it again reports no changes.
2. `story-architect hermes status` is all green.
3. In Hermes (CLI with the profile, and Desktop if possible): ask the agent about the demo project; it uses the app's tools and answers correctly from the data.
4. Ask the agent to stage and commit a change through the draft protocol; the DB changes, the browser shows the "updated" indicator, and refreshing shows the new data.
5. Ask the agent for the dashboard link; the URL opens the right project.
6. Without the token, `/mcp` returns 401; a wrong `Host` is rejected.
7. Existing `SOUL.md` of the default profile is untouched after all of the above.
8. Suite green, ruff clean, no Hermes mentions outside the adapter, docs, and plan files.
