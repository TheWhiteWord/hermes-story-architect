# Phase 5 — Standalone rename script (NOT plugin code)

**Phase 5 of 7.** Starts only after `task_03_rename_vocabulary.md` is complete.

**Parallelisable:** independent of phase 4. Once phase 3 has renamed the kinds in code, this
script can be written and run while phase 4 is in progress — it touches only stored rows,
which phase 4 does not change. Flagged here per the task's standing rule.

## Hard constraint

**This script does not ship in the plugin.** The plugin has not been deployed, so there is no
installed database to be compatible with. It lives under `tasks/task_31/`, is run by hand, and
is never imported by `core/` or `tools/`. No compat shim, no dual-name support, no
version gate. When it has been run, it is finished — there is nothing to keep.

## What it does

One statement:

```sql
UPDATE relations SET kind='plot_resolution' WHERE kind='plot_payoff';
```

That is the whole rename. `plot_setup`, `plot_crisis`, `plot_climax` keep their names;
`plot_complication` is new and has no rows to rewrite.

## Verified: the script is for the LIVE project only

An earlier draft listed **two** target databases. That was wrong, and following it would have
double-applied work:

| database | how it gets fixed | script needed? |
|---|---|---|
| `tests/fixtures/save-the-children` | phase 3 **regenerates** its DB from the edited markdown | **No** — never holds a `plot_payoff` row |
| `browser-verification-test` (live) | no regeneration path in this task | **Yes** — 2 rows |

Phase 3 decided to edit the fixture markdown and regenerate its committed DB from it. That
write produces `plot_resolution` rows directly, so by the time this script runs the fixture
has nothing to rename. Running it against the fixture anyway would rewrite 0 rows — harmless
but a misleading "1 row rewritten" claim in the output.

**Single target: the live project.** 2 rows.

## Verified: what the script must NOT touch

- **`entities.extra`** — plot role data is not stored there. It lives in `relations`. Verified:
  `columns_for_insert` (`entity.py:366`) skips relation fields, and `db.py:1114` reads plot
  characters from `extra` while roles come from `rel_map`.
- **Markdown files** — the live project's `plots/*.md` are produced by `story_export`. They
  are regenerated by re-exporting, not by this script. Editing them by hand would leave the
  DB and the markdown disagreeing.
- **`.story/index.yaml`** — deleted in phase 3 as dead code.

## Ordering caveat, and it matters

Phase 3 renames the kinds **in code** and this script renames them **in the databases**. Run
this script **after** phase 3 lands, or the code will read `plot_payoff` rows it no longer
recognises and every plot role silently disappears from the dashboard. Between phase 3
landing and this script running, the databases are in a state the code does not understand —
so do not run the plugin against them in that window.

If both happen in one sitting: land phase 3, run the script, then continue. Nothing else in
the suite touches these databases.

## Tests

No test. This is a one-shot script against two known databases, not shipped code; a test

Do not add a test asserting the rename "works" — that tests SQLite, not this code.
