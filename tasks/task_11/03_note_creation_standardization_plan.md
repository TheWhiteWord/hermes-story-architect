# Note Creation Standardization — Option A Plan

> Goal: Every note and index entry has all expected fields present, regardless of
> conversation context. Eliminate drift between what the LLM discusses and what
> ends up in the index.

## Problem

Today `story_create` passes LLM-provided frontmatter straight to the note. If the
LLM doesn't mention `knowledge` or `relationships`, they're absent from the note
and therefore absent from the index. The index becomes an incomplete context
window for future LLM turns.

## Solution: Tool-level schema enforcement

Add `ENTITY_SCHEMAS` to `core/constants.py`. Both `story_create` and
`story_edit._create_entity` merge user input over schema defaults.

Note content sections are already auto-generated by `_get_standard_sections()`.
This plan ensures that behavior is consistent across both create paths.

## Implementation

## Schema with field descriptions

The schema should be self-documenting — each field carries its type, default,
and a short description. This makes the tool fully understandable without
external reference files.

```python

        "name": {"type": "string", "default": "", "description": "Character display name"},
        "story_role": {"type": "string", "default": "", "description": "Protagonist/Antagonist/Supporting/Minor/Cameo"},
        "one_sentence": {"type": "string", "default": "", "description": "One-line description for index"},
        "relationships": {"type": "list", "default": [], "description": "List of {id, label, feeling}"},
        "goals_short": {"type": "string", "default": "", "description": "Short-term goal"},
        "goals_long": {"type": "string", "default": "", "description": "Long-term goal"},
        "knowledge": {"type": "list", "default": [], "description": "Facts the character knows"},
    },
    "location": {
        "name": {"type": "string", "default": "", "description": "Location display name"},
        "one_sentence": {"type": "string", "default": "", "description": "One-line description for index"},
    },
    "world": {
        "name": {"type": "string", "default": "", "description": "World display name"},
        "one_sentence": {"type": "string", "default": "", "description": "One-line description for index"},
        "rules": {"type": "list", "default": [], "description": "World rules"},
    },
    "plot": {
        "name": {"type": "string", "default": "", "description": "Plot display name"},
        "one_sentence": {"type": "string", "default": "", "description": "One-line description for index"},
        "status": {"type": "string", "default": "active", "description": "active/resolved/abandoned"},
        "characters": {"type": "list", "default": [], "description": "Character slugs (frontmatter-only)"},
```

### Merge logic

```python
schema = ENTITY_SCHEMAS.get(entity_type, {})
merged = {}
for field, meta in schema.items():
    merged[field] = frontmatter_data.get(field, meta["default"])
```

### Tool schema exposure

The `story_create` tool's JSON schema can include field descriptions:

```python
SCHEMA = {
    "type": "object",
    "properties": {
        "entity_type": {
            "type": "string",
            "enum": ["character", "location", "world", "plot"],
        },
        "slug": {"type": "string"},
        "frontmatter": {
            "type": "object",
            "description": "Frontmatter fields. See ENTITY_SCHEMAS for expected fields.",
            # Optionally inject per-entity field descriptions dynamically
        },
    },
}
```

This way the LLM can discover what fields exist and what they mean
**without reading any reference file**.

## Empty vs Null

Use **empty values** (`""`, `[]`), not `null`/`None`:
- YAML serializes `""` as empty string (clean)
- YAML serializes `[]` as `[]` (clean)
- Index generator can check `if field:` to skip empty
- Avoids `None` → `"None"` serialization bugs in YAML
