## Core Principles

1. **The test file IS the spec.** `tests/test_fountain_lexer.py` lists every function in the import block. Every one of those functions must be implemented. No more, no less.

2. **`expected_output.json` is ground truth.** `tests/fixtures/save-the-children/expected_output.json` was generated by running the actual Better Fountain parser. Your Python output must match it exactly. If your output differs, you're wrong — not the reference.

3. **Tasks are sequential.** Don't start Task N until Task N-1's gate passes. Each task builds on the previous one.

4. **Don't preserve existing bugs.** The current `core/fountain_lexer.py` has known bugs (swapped name/time_of_day, broken boneyard state caching, no dual dialogue lookback). Fix them — don't work around them.

5. **Don't over-engineer.** Port what the consumer needs (see `plan.md`). Don't add features "for later." If it's not in the test, don't build it.

6. **Verify against the reference, not your understanding.** When in doubt, run the BF parser via Node.js and compare. Don't guess what the output should be.

## Critical: What "Faithful Port" Means

- **Same token types** as BF (not similar — same)
- **Same token order** as BF
- **Same field values** as BF (where the consumer needs them)
- **Same behavior** on edge cases (boneyard, dual dialogue, forced headings)

It does NOT mean:
- Same variable names
- Same code structure
- Same comments
- Same class hierarchy

Port the behavior, not the implementation.

---

## When You Get Stuck

1. Run the BF parser on the same input
2. Compare the JSON output to what your code produces
3. Find the divergence
4. Fix your code to match

Don't try to understand why BF does something a certain way — just match the output.
